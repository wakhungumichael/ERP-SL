6. VERY IMPORTANT: WEIGHT CAPTURE / INTEGRATION LOGIC
==================================================

The system MUST preserve and use our current backend-based weight capture approach.

The frontend must not directly talk to random external indicator APIs unless explicitly required by backend design.

The preferred flow is:
Frontend -> our Django API -> integration resolution -> actual indicator source

Meaning:
- tenant and branch determine which indicator integration to use
- the backend resolves integration endpoints from configured IntegrationEndpoint records
- the frontend consumes the backend APIs only

The UI must support these existing backend capabilities:

A. Live weight
Use:
- GET /api/commercial-weighbridge/live-weight/

Purpose:
- fetch current live weight resolved through tenant/branch indicator integration

Expected concept:
- returns reading info like weight/value, unit, stability, branch context

B. Workflow context
Use:
- GET /api/commercial-weighbridge/transactions/workflow-context/?vehicle_id=<id>

Purpose:
- determine whether vehicle has pending first weight / valid recent first weight
- prepare second weight flow correctly

C. Transactions list/detail
Use:
- GET /api/commercial-weighbridge/transactions/
- GET /api/commercial-weighbridge/transactions/<id>/

D. Create transaction
Use:
- POST /api/commercial-weighbridge/transactions/

Expected business payload concept:
- branch
- customer
- vehicle
- item
- operator
- vehicle_type
- destination
- weight_type
- payment_mode
- payment_status
- manual_weight_capture
- weight_reason if needed

E. Stable capture onto transaction
Use:
- POST /api/commercial-weighbridge/transactions/capture-weight/

Purpose:
- capture stable weight via backend integration logic for a selected transaction

This is critical:
The system must be able to capture weight using the API here, through the backend workflow.
Do not replace this with a fake client-side simulation.
Do not remove this endpoint behavior.
